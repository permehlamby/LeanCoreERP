# Platform Mapping

Status: DRAFT v0.2. Task 2 of the agreed work order. Maps the technology-neutral specs (ADR-001) to a first physical platform. Builds on 00 v0.4, specs 02 to 09, 12, 15, 18 and ADR-001 to ADR-207. ADR-208 to ADR-218 are ACCEPTED (2026-10-19). The deltas of section 15 are applied to 00, 02, 09, 12, 15 and 18 (2026-10-19), except the new error code in 06 (see section 15). The proofs of concept of section 13 are still open.
Scope: database, tenant isolation, concurrency and locks, hashing, outbox and jobs, API layer, reads and search, timestamp service, object storage and encryption, package signing and repository, availability and restore.
Out of scope: cloud vendor, implementation language and framework, CI/CD, monitoring products, cost model, UI. Those are listed as open choices in section 14.

**Caution.** Product capabilities named here (PostgreSQL features, KMS algorithms, timestamp authorities, object lock) come from general knowledge and are UNVERIFIED against current vendor documentation. Section 13 lists what to verify with a proof of concept before the decision is final. Throughput figures are estimates, not measurements.

## 2. Database (ADR-208)

PostgreSQL is the reference platform of release 1. Reasons, each tied to a requirement of the specs:

| Requirement | Source | PostgreSQL feature (UNVERIFIED in detail) |
|---|---|---|
| Row-level isolation in the data layer | 00, P7 | Row-level security with forced policies |
| Serialisation point per chain by a row lock, fixed lock order | 02, 9.2, 04, 6.3 | `SELECT ... FOR UPDATE`, `FOR SHARE`, `lock_timeout` |
| No DELETE grant, no change of L1 columns | 02, 10, ADR-001 | Table and column privileges, triggers |
| `contains` filter, case- and accent-insensitive, at least 3 characters | 09, 2.4.1, ADR-092 | `pg_trgm` GIN index on a normalised column |
| Reads on replicas with read-your-writes | 09, Q2 | Streaming replication, application-level freshness check |
| Point-in-time recovery | 12, 18 | Continuous archiving |

Portability stays a design rule: the specs use no PostgreSQL-specific type (ADR-001). Only this spec and the migration scripts name the platform.

### 2.1 Type mapping

| Spec type | PostgreSQL | Notes |
|---|---|---|
| `ID` | `uuid`, version 7 (time-ordered), generated by the core | No database sequence: ids are known before the insert, so an idempotent retry reuses them. Time ordering keeps the leading `tenant_id, id` indexes local |
| `AMT` | `numeric(19,4)` | Never floating point. Amounts leave the API as decimal strings |
| `RATE` | `numeric(19,10)` | |
| `CODE` | `text` with a `CHECK` against a code table or a fixed list | No database enum types: adding a value must be a data change, not a type change |
| `TEXT(n)` | `varchar(n)` | |
| `TS` | `timestamptz`, always UTC | Microsecond precision. Written from the database clock (`transaction_timestamp()`), see 12 |
| `BINARY(32)` | `bytea` with `CHECK (length = 32)` | Hashes |
| `BLOB` | `bytea` (small) or an object reference | Timestamp tokens are small enough for `bytea` |
| `BOOL`, `DATE`, `INT`, `BIGINT` | as named | `BIGINT` for every `chain_seq`, `event_seq`, `ledger_seq` and outbox position |

Collation: `C` or a deterministic ICU collation for all key and code columns. Text comparison of keys never depends on locale. Search uses the normalised columns of section 8.

## 3. Isolation and database protection (ADR-209)

**Tenancy model.** One shared schema for all tenants. `tenant_id` is the first column of every key and index (00, P7). The tenant registry, the deletion certificate and the platform tables live in a separate `platform` schema without `tenant_id`.

**Row-level security.** Every tenant table has `ENABLE` and `FORCE ROW LEVEL SECURITY` and one policy `tenant_id = current_setting('app.tenant_id')::uuid`. The core sets the value with `SET LOCAL` as the first statement of every transaction, from the validated token, never from the request body. A connection pool therefore cannot leak a tenant across transactions. A query without the setting returns no rows and fails every write.

**Roles.**

| Role | Purpose | Rights |
|---|---|---|
| `core_owner` | Migrations only. Owns all objects | Not used at runtime. Not reachable from the application |
| `core_app` | Command and read API | `SELECT`, `INSERT` on transaction tables. Column-level `UPDATE` on the L2 and S columns only. No `DELETE`, no `TRUNCATE`. Subject to RLS |
| `core_job` | Anchor, outbox relay, export, search-column clearing jobs | As `core_app`, plus the update of S columns of the job tables |
| `core_retention` | Retention job and tenant deletion (ADR-073, ADR-124) | The only role with `DELETE` and with `UPDATE` on personal data columns. Used only by the retention and deletion workers, audited to the outbox |

**Command roles.** The four roles above are the **login roles** of the processes. The finer command roles of 02, section 10 (change command, posting, clearing, period, VAT return, stock, fulfilment, anchoring job, retention job) are **group roles** without login. Each login role is a member of the group roles of the commands it runs, and the per-table grants of 02, 10 are made to the group roles.

**Triggers.** The column-class triggers of 02, section 10 (D2, ADR-146: L1 reject, L2 reject when hard-closed or without `change_log` row, S only for the owning role with the owning event) are kept as they are. In addition, append-only tables (`change_log`, `period_event`, `clearing_item`, consumption rows, `chain_anchor` except the stamping update) get a `BEFORE UPDATE OR DELETE OR TRUNCATE` trigger that raises an error. Triggers are not used for business logic. Grants, triggers and `chains:verify` are three layers: a privileged user who disables a trigger is still caught by the hash chain and the anchors (02, 9.5).

## 4. Concurrency and locks (ADR-210)

- **Isolation level.** `READ COMMITTED`. The specs define one authoritative lock order (04, 6.3: orders, `item_company`, number counters, chain heads sorted by chain type then scope, open items by id, `outbox_head` last) and a derivation phase after the locks. With these locks taken first, a stronger isolation level adds retry cost and no safety. The commands never rely on snapshot reads for a decision made after the locks.
- **Lock timeout.** `lock_timeout` is set per transaction (default 5 seconds, a tenant-independent platform setting). A timeout returns a retryable error with the code of 06 (retryable flag), never a partial result. `deadlock_timeout` stays at the default. A deadlock is a defect of the lock order and is logged as such.
- **Gapless numbers.** The number counter is a row (04). A database sequence is not used, because a sequence is not transactional and leaves gaps. The legal number is read, incremented and written under the row lock in the posting transaction.
- **Idempotency.** `UNIQUE (tenant_id, idempotency_key)` on each command table and the command log (ADR-059). The insert uses `ON CONFLICT` and returns the stored result. The key and the request digest are compared: the same key with a different request is an error, as in 06.
- **Throughput.** A chain is a serial queue: its rate is bounded by the commit latency of the cluster, because the next posting waits for the head lock. With a synchronous standby (section 12) a commit takes in the order of milliseconds, so a single ledger chain carries in the order of hundreds of postings per second, not thousands (estimate, UNVERIFIED). Other companies and ledgers have their own chains and do not wait. Release 1 needs no change for this. The load test of section 13 sets the real figure.
- **Long transactions.** No external call inside a transaction (A2). The post-batch command runs each item in its own transaction (ADR-062), so a batch never holds a head lock across items.

## 5. Hashing (ADR-211)

- SHA-256 is computed **in the core application**, not in the database. The canonical serialisation of 02, 9.3 (fixed column order, UTF-8, ISO dates, plain decimal strings with fixed scale, explicit NULL marker) is implemented once, in one library, selected by `hash_version`.
- The library has a published set of **test vectors** per `hash_version` (input rows and expected hashes), in the repository next to the specs. Any second implementation (an auditor's verifier, a migration tool) must reproduce them.
- `chains:verify` runs in the same library on a read replica or a restored copy. It never takes a write lock (share locks only on heads, 02, 9.2).
- Database-side functions such as `pgcrypto` are not used for hashing. A database function would put hash behaviour into a migration and make a platform change a chain event.

## 6. Outbox and jobs (ADR-212)

- **Outbox.** `outbox_event` and `outbox_head` are tables (15, 5). The position of an event is `outbox_head.last_position + 1`, taken under the head lock in the command transaction, last in the lock order (K3). Positions are gapless and commit-ordered, so a reader that has seen position n has seen all events up to n and cannot skip one that commits later. That property is why a database sequence is not used.
- **Delivery.** Release 1 has no message broker. The app feed of 15 is a cursor read over the outbox (`after` position). A webhook relay is a job that reads from the cursor and delivers with retry. `LISTEN/NOTIFY` may wake the relay, but it is a hint only and never the source of truth.
- **Job runner.** All background work (anchors, relay, retention, export, clearing of search columns, package validation of large packages) is a queue table processed with `SELECT ... FOR UPDATE SKIP LOCKED` by separate worker processes. Schedules are rows. A worker that dies loses its lock at the end of the transaction and the job is picked up again, so every job is idempotent by design (a job has an idempotency key like a command). No second infrastructure component is added.
- **When to add a broker.** When the number of consuming apps or the volume of events makes the cursor reads a measurable load on the primary. The outbox stays the source: a broker would be fed from it.

## 7. API layer (ADR-213)

| Topic | Decision |
|---|---|
| Style | HTTPS and JSON. Resources as in 06 and 09. Commands as `POST /v1/{resource}:{verb}` (for example `journal-documents:post`), matching the command names of the specs |
| Contract | OpenAPI 3.1. The command contracts of 06 and the read contracts of 09 are the source, the OpenAPI document is generated from them and published with every release. Error codes are an enumeration in the document |
| Authentication | OAuth 2.0 and OpenID Connect. Users and services present a signed JWT bearer token. Services use client credentials. The token carries the tenant. A request for another tenant than the token's is rejected before any query |
| Authorisation | The permission names of 06 and 07 are scopes or roles of the token. Checked in phase P0 of the command pipeline (ADR-058) |
| Idempotency | Header `Idempotency-Key` carries `idempotency_key`. A body value, if present, must equal it |
| Errors | `application/problem+json`. One entry per error with the stable code, request path, parameters, phase and retryable flag, up to 100 (ADR-058). No localised text |
| Pagination | Keyset cursors on the stable keys of 09. No offset. The cursor is opaque and signed |
| Versioning | `/v1` in the path. Within a major version only additive changes. The `hash_version`, package `format_version` and API version are independent |
| Limits | Request size and batch size (500 items, 06, Q11) at the gateway and in the core. Per-tenant rate limits at the gateway |
| Transport | TLS 1.2 or higher. Mutual TLS optional for service identities. The core is not exposed to the public internet without a gateway |
| Time | All timestamps in UTC, ISO 8601 with `Z`. Dates are plain dates |

The implementation language and framework are not decided here (section 14). Constraints on the choice: exact decimal arithmetic, a SHA-256 and RFC 3161 implementation, JSON handling with fixed-scale decimal strings, and the ability to hold the OpenAPI document as a build artefact.

## 8. Reads, replicas and search (ADR-214)

**Replicas and freshness.** Reads may run on a streaming replica (09, Q2). The caller passes `min_ledger_seq`. The core reads the `last_seq` of the LEDGER `chain_head` row on the serving database. If it is lower, the read returns `READ.STALE_SNAPSHOT` (retryable). The check needs no replication-internals access, and works with any replica technology.

**`contains` search (ADR-092).**

1. The core computes a **normalised search column** at write time, in application code: Unicode NFKD, remove combining marks, case-fold, collapse whitespace. This is a deterministic function in the same library as the hash, so it does not depend on the database's `unaccent` configuration.
2. The column has a GIN index with `pg_trgm`. A filter of at least three characters uses the trigram index.
3. The scope guard of ADR-092 (company plus a date range, an account, a partner or a number range) keeps the candidate set small, so the index is a help and not the only protection.
4. Search columns of personal data are cleared by the retention job and are never hashed (ADR-092, 12). They are excluded from backups of exports.

If a future platform cannot offer the index, `contains` is disabled for the field and returns `READ.INVALID_FILTER` (09, 2.4.1).

## 9. Timestamp service (ADR-215)

- **Mechanism.** The `chain_anchor` row is written in the transaction of the command (state PENDING, A2). An anchor job sends `anchor_digest` to the timestamp authority as an RFC 3161 request and stores the response token, the authority id, `stamped_at` and the location in object storage (`anchor_ref`). A close never waits for the authority.
- **Authority.** Production uses a **qualified timestamp authority of the EU trust list** (eIDAS), so the token has the legal presumption of accuracy of the date and time. The vendor is a procurement choice. Development and test use a non-qualified authority. Rehearsal tenants are not anchored externally (ADR-134).
- **Why one authority in release 1.** The `chain_anchor` row has one token column. Two authorities would need a child table. The residual risk (one authority's outage or failure) is covered by the retry job and by the PENDING deadline warning of 02, 9.5. A second authority is a later extension: a new table `chain_anchor_token`, no change to the hash.
- **Verification.** A verifier needs only the token, the digest and the authority's certificate chain. Neither needs the core or a key held by the core (02, 9.5). The certificate chain and the revocation data of the authority at stamping time are stored with the token in object storage, so a token stays verifiable after the certificate expires.
- **Retry.** Exponential backoff, a failed attempt is logged as an audit event, and an anchor older than `anchor_pending_deadline` raises a warning in `chains:verify` and an alert.
- **Clock.** All database and application hosts take time from a platform NTP source. The authority's time is the evidence, the system clock is not.

## 10. Object storage and encryption (ADR-216)

| Topic | Decision |
|---|---|
| Location | One EU region bucket set per environment: `exports`, `anchors`, `packages` |
| Layout | Key prefix `{tenant_id}/...` for exports and anchors. `export_storage` of 07 holds the prefix reference, never credentials (12, 7.1) |
| Access | The core and jobs use a service identity with a role limited to these buckets. Callers get **short-lived pre-signed URLs**. No credentials are stored in the core's tables |
| Encryption in transit | TLS 1.2 or higher everywhere |
| Encryption at rest | Database volumes, backups and buckets are encrypted by the platform. Exports and anchor material additionally use **envelope encryption with a key per tenant**, held in the KMS. Destroying the tenant key at tenant deletion makes the exports unreadable (crypto-shredding) |
| Object lock | Compliance-mode object lock **only for the `anchors` and `packages` buckets** (tokens, certificate chains, digests, signed archives). They contain no personal data, so the lock does not conflict with erasure. Exports and the personal data inside them are never locked and expire by the lifecycle rule of the retention settings |
| Integrity | Each export has a manifest with a SHA-256 per file (12, 7). The manifest hash is recorded in the export job row |

## 11. Package signing and repository (ADR-217)

This closes Q5 of 18.

**Archive.** A package is a deterministic archive (sorted entries, fixed timestamps, no extra metadata) of the directory of 18, section 4, plus a `signing-manifest.json` that the signing tool generates (it is not authored). It lists every file with its SHA-256 and copies `package_code`, `package_version`, `format_version` and `state` from `package.json`. The package manifest of 18 (`package.json`) stays the authored manifest. The core rejects an archive whose copied fields differ from `package.json` or whose `state` differs from the state of `verification.json`.

**Signature.** A detached signature over the canonical bytes of `signing-manifest.json`. Algorithm: ECDSA with the P-256 curve and SHA-256. The choice is conservative because cloud KMS and HSM products support it widely (UNVERIFIED per product). The private key lives in a KMS or HSM and is never exported. Signing is a platform-team operation behind a **two-person rule**: the package owner and the reviewer of the verification record approve, the platform team signs.

**Two trust sets.** The core holds public keys in two sets, selected by the tenant `purpose` (07, 5.1: PRODUCTION uses the release set, TEST and REHEARSAL the development set):

| Trust set | Keys accepted | Tenants |
|---|---|---|
| Development | development key and release key | TEST and REHEARSAL tenants |
| Release | release key only | PRODUCTION tenants |

A package that becomes DEPRECATED (18, 6) keeps its archive and signature. DEPRECATED is recorded in the signed `index.json`, not in the archive, and the core still accepts the archive for companies that already use it.

Only archives whose `verification.json` is RELEASED are signed with the release key. The gate of 18, section 6 ("PRODUCTION accepts only RELEASED") is therefore enforced twice: by the state in the signed manifest and by the key (`PACKAGE.NOT_RELEASED` and the new `PACKAGE.SIGNATURE_INVALID`). A DRAFT archive can never carry a signature a production core accepts.

**Verification at apply.** `config-packages:validate` and `:apply` check, in this order: the signature against the trust set, the SHA-256 of every file against the signing manifest (`PACKAGE.DIGEST_MISMATCH`), the copied fields against `package.json`, the `format_version`, the `requires` ranges and the verification gate. A failure is a package error of 18 (`PACKAGE.*`). The core records the manifest hash, signer key id and archive hash in the package record and in `applied_config_package_item`.

**Key lifecycle.** Keys have an id and a validity period. A rotation adds the new public key to the trust set before the first signature with it. A compromised key is removed from the trust set by a core release (revocation list in the same artefact). A package signed with a removed key can still be shown as applied history, but cannot be applied again.

**Repository.** A versioned object store (the `packages` bucket) with an immutable path `{package_code}/{package_version}/{package_code}-{package_version}.tar` plus a signed `index.json`. A published version is never overwritten (object lock in compliance mode, no personal data). A tool of the platform team uploads the archive to the core API for apply: **the core never fetches packages from the network**, so it needs no repository credentials and no outbound path to the repository. Archive size limit 20 MB (DK v0.3.0 is far below, UNVERIFIED estimate).

**What is not signed.** User changes after apply are ordinary configuration with the audit trail (18, 7). The signature covers what the platform delivers, not what the tenant does with it.

## 12. Availability, backup and restore (ADR-218)

- **Topology.** Primary and a **synchronous standby in a second availability zone** of the same region. A commit returns after the standby has the data, so a failover loses no committed posting. Read replicas are asynchronous and are covered by the freshness check of section 8.
- **Backup.** Continuous archiving with point-in-time recovery. Retention of backups and archives: 35 days (proposal). A cross-region copy of backups for disaster recovery. A restore drill at least once per release cycle.
- **Targets (proposal, not a promise).** Zone failure: RPO zero, RTO in minutes by automatic failover. Region loss: RPO in minutes (asynchronous copy), RTO hours.
- **Restore reconciliation.** Restoring a database to an earlier point can lose committed postings that were already visible: in the outbox feed that apps consumed, in an anchor sent to the authority, or in a document number given to a customer. The recovery procedure therefore is mandatory:
  1. Restore into a **new** database, not over the old one.
  2. Run `chains:verify` on every chain and compare the heads with the newest stamped anchors. A head older than an anchor proves lost postings.
  3. Compare consumer positions of the outbox with `outbox_head`. Apps that read beyond it must be told (this is the one case where the position stream is re-issued, and the apps' idempotency keys protect against duplicates).
  4. Report the lost range to the tenants. No lost posting is silently re-created.
  The restore is a platform operation with a documented approval, not a core command.
- **Erasure lag.** Backups hold data of deleted tenants and anonymised persons until the backup retention ends (35 days). The deletion certificate (ADR-124) and the privacy notice state this period. Crypto-shredding of the tenant key covers exports and anchor material, not database backups.
- **Schema migrations.** Forward-only, run by `core_owner` in a controlled step. A migration never rewrites an L1 column and never changes a hashed value. A change of hash input is a new `hash_version` (ADR-204), not a migration.
